# 請求書の集計対象を「発送済みのみ」に変更する

## 背景

現在、請求書は `InvoiceService::SALES_STATUSES = [2, 3, 5, 6]`（代理店処理済み・本部処理済み・発送待ち・発送済み）の注文を、**注文日（`orders.created_at`）の月**で集計している。同じ定数が `Admin\SalesController` にも重複して定義されている。

実態として未発送の商品まで請求されてしまうため、**発送済み（ステータス6）の商品だけを請求対象**にしたい。

## 決定事項

| 論点 | 決定 |
|---|---|
| 対象ステータス | 発送済み（6）のみ。2・3・5 は対象外 |
| 月の振り分け | 発送日基準（注文日基準から変更） |
| 過去分の扱い | カットオフは設けず、全期間に適用する |
| 管理画面 | 請求額に関わる集計のみ新基準。売上分析系は現状維持 |

### カットオフを設けなかった経緯

当初は「送信済みの請求額を後から動かさない」ことを優先し、カットオフ（この日以降に作成された注文から新ルール）を設けていた。2026-09-01 で設計し、クライアントの要望で 2026-07-01 に前倒しした。

しかしカットオフは注文日で切るため、**6/30 に注文して 7/2 に発送した注文が6月分の請求書に載る**という境界のずれを生む。クライアントの認識は「発送した月に請求」なので、この形は問い合わせにつながった。カットオフを動かしても境界が別の月へ移るだけで、同じ問題が毎月起きる。

そこでカットオフを撤廃し、全期間を発送日基準に統一した。二重計上の心配は無い。1件の注文には発送日がひとつしかなく、必ずただ一つの月に属するためである。

この判断ができたのは、本番データで **未発送（ステータス 2・3・5）の注文が全月ゼロ**だったことによる。旧ルールの対象 `[2,3,5,6]` のうち実際に存在したのは 6 だけで、旧ルールも実質「発送済みのみ」を集計していた。したがって全期間に適用しても**請求書から消える注文は無く**、変わるのは月の振り分けだけになる。

### 過去の請求書が変わることについて

請求書は DB に保存されず、閲覧のたびに再計算される。そのため過去月の請求額も新ルールで計算し直される。月をまたいで発送された注文は発送月へ移動するため、すでに LINE 送信済みの月の金額が変わる。クライアントから「現在確認できる請求額が変わっても構わない」との合意を得ている。

## 設計

### 1. データモデル

`orders` テーブルに以下を追加する。

- `shipped_at`（datetime, nullable, インデックス付き）

書き込みルール：

- ステータスが **6 以外 → 6** に変わったとき `now()` を記録する
- ステータスが **6 → 6 以外** に変わったとき `null` に戻す（誤操作のリカバリ）
- すでに 6 のまま再保存された場合は既存値を維持する（発送日が動かないようにする）

書き込み箇所は管理画面の 2 メソッドのみ：

- `Admin\OrderController::updateStatus()` — 単票更新
- `Admin\OrderController::bulkUpdate()` — 一括更新（`Order::whereIn()->update()` の一括 UPDATE に `shipped_at` も含める）

`Agency\OrderController` はステータス 6 を設定できないようにする。`updateStatus()` には `in:1,2,3,9` のバリデーションがあるが `bulkUpdate()` には無かったため、同じものを追加する。ここが抜けていると `shipped_at` を伴わずに 6 が書き込まれ、その注文がどの月の請求にも載らなくなる。`Admin\OrderController::bulkUpdate()` も同様に無検証だったため `in:2,3,4,5,6,9` を追加する。

`shipped_at` は列を追加した時点より前に発送された注文では空になる。全期間を発送日基準にするため、**発送済み注文すべてにバックフィルが必要**。埋めないとその注文は請求から落ちる。

バックフィルは `activity_logs` から復元する。`logOrderStatusUpdated()` がステータス変更のたびに `new_status` と時刻を記録しているため、`new_status = 6` の**最新**のレコードが最後に発送済みになった時刻になる（コントローラ側の書き込みと同じ意味になる）。本番では発送済み 464 件のうち 463 件がログから復元でき、残る 1 件は `updated_at` にフォールバックする。

バックフィルはマイグレーションで行う。デプロイは `git pull` の後に `php artisan migrate --force` が走るため、コードの切り替えとデータの整備が同じタイミングで揃い、「新ルールは有効だが `shipped_at` が空」という状態ができない。

マイグレーションからは `InvoiceService` の定数を参照せず、日付とステータスを直接書く。マイグレーションは適用済みの履歴であり、後からアプリ側の定数が変わっても意味が動いてはいけないため。

### 2. 集計ロジック（`InvoiceService`）

定数は以下の2つ。

```php
/** 売上分析で対象とするステータス（保留=4以外の確定注文）。請求の集計には使わない */
public const SALES_STATUSES = [2, 3, 5, 6];

/** 発送済み */
public const SHIPPED_STATUS = 6;
```

現在 `monthlyBreakdown()` / `hasInvoice()` / `forMonth()` の 3 箇所に同じ `whereIn('status', self::SALES_STATUSES)` がコピペされている。これを `InvoiceService` の **public static メソッド 1 本**（クエリビルダを受け取って条件を適用して返す）にまとめ、3 箇所から呼ぶ。`Admin\SalesController` も同じメソッドを使う。

請求の条件は `status = 6` かつ `shipped_at IS NOT NULL`、計上月は `shipped_at` の月。`SALES_STATUSES` は売上分析側にだけ残る。

`monthlyBreakdown()` は月ごとにグループ化する際、注文の `created_at` ではなく `shipped_at` で月を決める。「当月は未確定」の判定（`< Carbon::now()->startOfMonth()`）も `shipped_at` に対して行う。

`isFixedMonth()`、`aggregate()`、`invoiceUrl()` は変更しない。確定タイミング（当月は未確定、前月まで）も現行どおり。

### 3. 管理画面（`Admin\SalesController`）

請求額に関わる集計だけを新基準に合わせる。判定条件は §2 の `InvoiceService` の public static メソッドを呼び、条件の重複定義を作らない。`SalesController` は `DB::table` の生 join を使っている箇所があるため、このメソッドは Eloquent ビルダと `DB::table` ビルダの双方で使えるよう、テーブル別名（`o.` など）をプレフィックスとして受け取れるようにする。

**新基準にする（請求）**

| 箇所 | 内容 |
|---|---|
| `index()` `$merchantSales`（:71） | 加盟店ごとの請求額一覧。振込確認・督促と並ぶ |
| `show()` `$orders`（:183） | 加盟店の月次明細・合算コピー |
| `invoice()` `$orders`（:260） | 請求書そのもの |

**現状維持（売上分析）**

| 箇所 | 内容 |
|---|---|
| `index()` `$productSales`（:34） | 商品別売上 |
| `index()` `$headquartersProcessed`（:52） | 本部処理済み集計 |
| `index()` `$shippingFeeCount`（:61） | 送料発生件数 |

この切り分けにより、画面上の「総合計」（分析系の `$grandTotal`）と加盟店別売上一覧の合計が一致しなくなる。誤解を避けるため、加盟店別売上一覧の見出し付近に「発送済みのみ集計」の注記を追加する。

`SalesController` に重複している `private const SALES_STATUSES` は削除し、`InvoiceService` の定数を参照する。

### 4. 影響を受ける他の経路

以下は `InvoiceService` を経由しているため、修正なしで新ルールが反映される。

- `SendMonthlyInvoiceLine`（月次の請求書 LINE 送信バッチ）
- `PaymentReminderSender`（振込督促）
- 加盟店側 LIFF の請求書一覧・請求書ページ（`MerchantController::getInvoiceList()` / `invoicePdf()`）

## エッジケース

- **注文が発送されないまま滞留する** — どの月の請求にも計上されない。既存の管理画面「発送待ち」一覧で追える前提とし、新たな滞留検知は作らない。
- **請求送信後にキャンセルされる（6 → 9）** — `shipped_at` が null に戻り、送信済み月の請求金額が減る。請求書は再計算方式のため避けられない。運用で対応する。
- **月末に発送済みにして翌月に戻す等の操作** — `shipped_at` は最後に 6 になった時刻で上書きされ、計上月も移動する。上と同じく再計算方式の帰結として許容する。

## やらないこと

- ステータス 6 になったことが一度も無い注文への `shipped_at` 補完
- 請求書のスナップショット保存（再計算方式の変更）
- 売上分析系の集計基準の変更
- 発送滞留の検知・通知機能
