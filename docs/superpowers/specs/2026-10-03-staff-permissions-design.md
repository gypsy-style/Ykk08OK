# サロンスタッフの権限設計

- 作成日: 2026-10-03
- 状態: 設計承認済み（実装計画はこれから）

## 背景

サロンのスタッフ（`merchant_members`）は、今は全員同じ扱いで、注文と注文履歴の閲覧しかできない。
スタッフ管理・請求書確認・登録情報の修正はオーナー（`merchants.user_id`）だけができる。

オーナーがスタッフごとに権限をオン・オフし、オーナー以外にもこれらの操作を任せられるようにする。

### 現状の整理

| 機能 | オーナー | スタッフ（現状） |
|---|---|---|
| 注文する | ○ | ○ |
| 注文履歴を見る（サロン全体の注文と金額） | ○ | ○ |
| 登録情報（サロン名・住所・口座名）の修正 | ○ | ✕ |
| スタッフ一覧・追加・削除 | ○ | ✕ |
| 請求書を見る | ○ | ✕ |

## 決定事項

- **権限を付けるのはオーナー**。LIFF の「登録スタッフ一覧」で切り替える。本部（管理画面）・代理店画面は今回触らない。
- **権限は5つで、それぞれ別にオン・オフする**。
- **権限を変えられるのはオーナーだけ**。スタッフ管理の権限を持つスタッフも、権限は見るだけで変えられない（スタッフ同士で権限を広げ合えないようにするため）。
- **初期値は今の動きを変えない**。今いるスタッフにも、これから追加するスタッフにも同じ初期値が入る。

## 1. データ

`merchant_members` に boolean 列を5つ追加する（マイグレーション1本）。

| 列 | 意味 | 初期値 |
|---|---|---|
| `can_order` | 注文する | true |
| `can_view_order_history` | 注文履歴を見る・注文詳細・キャンセル | true |
| `can_view_invoice` | 請求書確認 | false |
| `can_edit_merchant` | 登録情報の修正 | false |
| `can_manage_staff` | スタッフの一覧・追加・削除 | false |

列の初期値で今のスタッフにも新しいスタッフにも同じ値が入るので、データを移す作業はいらない。
`MerchantMember` の `$casts` に5列を boolean で追加する。

JSON の1列にまとめる案や、権限用の別テーブルを作る案もあったが、権限は5つで決まっていて、普通の列のほうが扱いやすいため採らない。

## 2. 権限の判定（1か所に集約）

`App\Services\MerchantAccess`（新規）を作り、「この人はどのサロンで何ができるか」をここで判定する。

- 入力: `User`
- 出力: 所属サロン（`Merchant`）、オーナーかどうか、権限5つ
- 判定ルール
  - オーナー（`merchants.user_id` が本人）→ 5つすべて true
  - スタッフ（`merchant_members.user_id` が本人）→ その行の列の値
  - どちらでもない → サロンなし、すべて false

今はコントローラーごとに「オーナーか、スタッフか」を調べる処理が散らばっている（`OrderController` に4か所、`MerchantController::getMerchantInformation` など）。権限を見る箇所は、これを `MerchantAccess` に置き換える。

**画面のボタンを隠すだけでなく、サーバー側でも必ず判定する。** LIFF の裏の API は、URL さえ分かれば誰でも呼べるため。

## 3. 画面とAPIの動き

### 3-1. マイページ（店舗情報）

- `get-merchant-information` のレスポンスに `permissions`（5つの真偽値）と `is_owner` を追加する。
- `liff_information.js` は、今のオーナー判定（`user_id == merchant_user_id`）をやめ、`permissions` を見てボタンを出す。
  - 「登録情報を修正する」← `can_edit_merchant`
  - 「登録スタッフ一覧」← `can_manage_staff`
  - 「請求書」← `can_view_invoice` かつ `has_invoice`（今と同じ）
- 登録情報を修正する画面の URL は、署名付き URL にしてレスポンスで返す（`can_edit_merchant` のときだけ）。→ 3-5

### 3-2. 登録スタッフ一覧（権限を切り替える画面）

- 開ける人: オーナーと `can_manage_staff` のスタッフ。`getMemberList` は今のオーナー限定をやめ、`MerchantAccess` で判定する。
- 各スタッフのブロックに、権限5つのチェックボックスを並べる。
  - **オーナー**: チェックを変えるとその場で保存する（保存ボタンなし）。成功したら「保存しました」と短く表示し、失敗したらチェックを元に戻してエラーを出す。
  - **`can_manage_staff` のスタッフ**: チェックは無効（`disabled`）で、見るだけ。
- 新しい API: `POST /api/merchant/member_permission`
  - 入力: `access_token`, `member_user_id`, `permission`（5つの列名のどれか）, `value`（真偽値）
  - 判定: 本人がそのサロンの**オーナー**であり、対象スタッフが**同じサロンのスタッフ**であること。どちらかでも違えば 403。
  - `permission` は5つの列名だけを受け付ける（それ以外は 422）。
- スタッフの削除ボタンは、オーナーと `can_manage_staff` に出す。**自分自身の行には出さない**。

### 3-3. 注文画面（`can_order` がオフ）

- リッチメニューは全スタッフ共通なので、注文ボタンは出たままになる。
- `api/merchant/member_rank` のレスポンスに `can_order` を追加する。`order/list.blade.php` のインラインスクリプトがこれを見て、オフなら商品一覧の代わりに「注文の権限がありません。サロンオーナーにご確認ください」を表示する。
- 注文の確定（`order.register` / `order.store`）でも `can_order` を判定し、オフなら止める。
- **`resources/js/liff.js` は変更しない**（変更禁止のファイル）。

### 3-4. 注文履歴・詳細・キャンセル（`can_view_order_history` がオフ）

- 履歴の取得は `liff.js` が `api/order/history` を呼び、返ってきた HTML をそのまま表示している。そこで `getOrderHistory` が、権限がない人には「注文履歴を見る権限がありません」の HTML を返す（ステータスは 200）。`liff.js` は変更しない。
- 注文詳細とキャンセルも同じ権限で守る。→ 3-6

### 3-5. 登録情報の修正（`can_edit_merchant`）

- `merchants.edit`（GET）と `merchants.update`（PUT）を、署名付き URL を必須にする（請求書の `merchants.invoice` と同じ仕組み）。
- 署名付き URL は、`get-merchant-information` が `can_edit_merchant` を持つ人にだけ発行する。
- 編集画面は、更新用の署名付き URL を Blade に埋め込んで、そこへ送る。
- `update` で受け付ける項目は今と同じ（`status` などは受け付けない）。

### 3-6. スタッフの追加・削除

- `storeMember`: 送られてきた `merchant_id` をそのまま信じない。本人の `access_token` から、そのサロンへの追加が許されるかを判定する。
  - この API は、追加される本人が QR を読んで呼ぶ。そのため、「追加する側」の権限ではなく、「正しい QR から来たか」で判定する。
  - **招待トークン**: `hash_hmac('sha256', 'staff-invite:' . merchant_id, config('app.key'))`。`getMemberList` が、開いた人（オーナーか `can_manage_staff`）にだけ、`merchant_id` と招待トークンを返す。QR の URL に両方を入れる。
  - 追加画面（`add_member`）は、`merchant_id` と同じように `liff_state` から招待トークンを取り出し、`storeMember` へ送る。`storeMember` は `hash_equals` で照合し、合わなければ 403。
  - Laravel の署名付き URL を使わないのは、LIFF を通すとクエリが `liff.state` に包まれ、`hasValidSignature()` でそのまま検証できないため。招待トークンに有効期限は付けない（今の QR も期限なしで、紙に印刷して使うこともあるため）。
  - すでにどこかのサロンのオーナーかスタッフである人は、追加しない（今は二重登録を防いでいない）。
- `destroy_member`: `access_token` を必須にする。本人がオーナーか `can_manage_staff` を持ち、対象が**同じサロンのスタッフ**で、**自分自身ではない**ときだけ削除する。

### 3-7. 注文詳細・キャンセル

- `order.detail` を署名付き URL を必須にする。履歴の HTML（`order/partials/history.blade.php`）でリンクを作るときに署名する。履歴を見られる人にしか履歴の HTML は返らないので、詳細へのリンクも権限のある人にしか渡らない。
- `order.cancel` も署名付き URL を必須にする。詳細画面を描画するときに、その注文用の署名付きキャンセル URL を埋め込む。
- 署名付き URL の有効期限は請求書と同じく1日（`Carbon::now()->addDay()`）。

## 4. あわせて塞ぐ、今ある穴

権限を作っても、次の穴が残っていると素通りできてしまうため、今回の範囲に含める。

| 箇所 | 今の問題 | 対応 |
|---|---|---|
| `DELETE /merchants/member/{id}` | 本人確認なし。ユーザーIDを指定すれば誰でもどのスタッフでも消せる | 3-6 |
| `POST /merchants/store_member` | 送られた `merchant_id` を信じて登録する。数字を変えれば別のサロンにスタッフとして入り込める | 3-6 |
| `GET /order/detail/{id}` | 本人確認なし。注文IDの数字を変えればどのサロンの注文でも見られる | 3-7 |
| `POST /api/order/cancel` | 本人確認なし。注文IDだけでどの注文でもキャンセルできる | 3-7 |
| `GET merchants/edit/{id}` / `PUT merchants/{id}` | 本人確認なし。IDの数字を変えればどのサロンの登録情報も見られて、書き換えられる | 3-5 |

## 5. エラー時の扱い

- 権限がない API 呼び出し: 403 と日本語のエラーメッセージを返す。画面にはメッセージを出す。
- 署名付き URL の期限切れ・改ざん: 請求書と同じく `merchants.invoice_expired` の画面に「このリンクの有効期限が切れています。LINEからもう一度開いてください。」を出す。
- 権限の保存に失敗したとき: チェックボックスを元の状態に戻してエラーを出す。

## 6. 確認方法

テストコードは書かない方針なので、ローカル（`LIFF_MOCK`）と本番の実機で次を確認する。

- オーナー: 5つのボタンがすべて出る。スタッフ一覧で権限を切り替えられ、再読み込みしても残っている。
- 初期値のスタッフ: 注文と注文履歴だけできる。マイページに3つのボタンが出ない。
- 各権限をオンにしたスタッフ: 対応するボタンが出て、操作できる。
- `can_manage_staff` のスタッフ: スタッフの追加・削除はできるが、権限は変えられない。自分自身は消せない。
- `can_order` をオフ: 注文画面にメッセージが出て、注文の API も通らない。
- `can_view_order_history` をオフ: 履歴にメッセージが出る。
- 4章の穴: 他人の ID・署名なしの URL では、見ることも操作することもできない。

## 7. デプロイ時の注意

- マイグレーションが1本あり、デプロイ時に `migrate --force` で自動適用される。追加するのは初期値付きの列だけなので、既存のデータは変わらない。
- `resources/js/liff_information.js` などを変更するので、ローカルで `npm run build` して `public/build` を FTP でアップロードする必要がある。
- **今まで配ったスタッフ追加用の QR・URL は使えなくなる**（招待トークンが無いため）。オーナーにスタッフ一覧から QR を出し直してもらう。
- 署名付き URL に切り替えると、切り替える前に開いていた詳細画面・編集画面の古いリンクは使えなくなる。開き直せば使える。

## 範囲外

- 管理画面・代理店画面からスタッフの権限を見る・変える機能
- 権限ごとにリッチメニューを出し分けること（注文ボタンは全スタッフに出たまま）
- オーナーの引き継ぎ（オーナーを別の人に変える）
